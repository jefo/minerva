# Build Economics — Capability

Оценивает не производительность ПК, а **стоимость владения выбранной инженерной стратегией**.

Ответ не «покупать или нет». Ответ — «какую финансовую стратегию реализует эта сборка».

## Три слоя движка

**Compute Layer** (детерминированный): цены из источников, совместимость, стоимость апгрейда. Данные: Minerva dim/ + pricing warehouse.
**Classification Layer** (model-based): gaming core vs visual layer, категории бюджета.
**Strategic Layer** (pure reasoning): ликвидность, риск устаревания, экономический диагноз. Интеграция с forecast-lifecycle.

## Price Source Strategy — КРИТИЧЕСКИЙ РАЗДЕЛ

**Model MSRP НЕПРИГОДЕН для российского рынка.** Production-валидация 2026-07-24:
- RAM DDR5: model = 8 700 ₽, реальность = 50 000 ₽ (ошибка 5.7×)
- GPU RTX 5070: model = 47 800 ₽, реальность = 65 000 ₽ (ошибка 1.4×)

**Каждая цена верифицируется до начала вычислений.** Актуальная стратегия:
- **Tier 1 (обязательный):** `pc-parts-price-check` через price.ru — browser_navigate → browser_console. Для GPU, CPU, PSU, кулеров, корпусов.
- **Tier 1-ram (особый):** price.ru смешивает ёмкости RAM → медиана бесполезна. ТОЛЬКО данные пользователя ИЛИ референсные обзоры.
- **Tier 2 (резервный):** `warehouse-pricing` когда наполнен реальными данными.
- **Tier 3 (fallback):** запрос пользователю. Честный пробел > fabricated цифра.
- **Запрещено:** model_msrp для российского рынка.

## Process

### 0. VERIFY PRICES (обязательный шаг — перед любыми вычислениями)
Для каждого компонента — загрузить `pc-parts-price-check`, проверить цены через price.ru. Если price.ru не дал результат — запросить у пользователя. Без верифицированных цен не продолжать.

### 1. Anchor: Minerva
Загрузить `dim/cpu/{id}.yaml`, `dim/gpu/{id}.yaml`, `dim/socket/{id}.yaml`.

### 2. Разрешить конфигурацию
Если пользователь не указал MB, RAM, cooler, PSU, storage — подобрать default'ы под платформу.

### 3. Compute Layer (§1, §5, §6)
- §1: `platform_cost = cpu + mb + ram + cooler` (без GPU)
- §5: max CPU на сокете, next-gen support, замена памяти/платы
- §6: что менять через 2-3 года, стоимость апгрейда

### 4. Classification Layer (§2, §3, §4)
- §2: бюджет по подсистемам, найти перекосы
- §3: gaming_core = CPU + GPU + RAM
- §4: visual_layer с rationale на каждый компонент

### 5. Strategic Layer (§7, §8, §9)
- §7: ликвидность — model-based по факторам
- §8: риск устаревания — интеграция с forecast-lifecycle
- §9: экономический диагноз — synthesis. Не «покупать/не покупать», а «стратегия X»

### 6. Deliverables
- `{build_id}.yaml` — structured profile (9 секций)
- `{build_id}_REASONING.md` — полная цепочка рассуждений: источники цен, методология, TCO-сценарии, key insight

## Output Contract

`references/build-economics-contract.yaml` — 9 секций.

## Pitfalls

1. **Цены без provenance — красный флаг.** Каждая цена маркируется источником. Model MSRP для РФ = запрещено.
2. **Platform lifecycle критичен.** LGA1700 legacy → апгрейд = CPU+MB+RAM. AM5 active → только CPU.
3. **Классификация visual layer требует rationale.** Показать ЧТО и ПОЧЕМУ не влияет на FPS.
4. **Экономический диагноз ≠ «покупайте».** Описывает стратегию.
5. **TCO-сравнение обязательно.** Минимум 2-3 сценария (альтернативная платформа/память). Без сравнения диагноз бесполезен.
6. **Price.ru для RAM — не использовать.** Смешивает ёмкости. Только пользователь или референсные обзоры.
7. **Не фабриковать цены «чтобы математика сошлась».** Сумма строк должна быть равна итогу. Неверифицированная цена с оговоркой > fabricated без оговорки.
