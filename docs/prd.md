# PRD: Knowledge Services — композиционный движок знаний

**Версия:** 0.1.0
**Статус:** draft
**Дата:** 2026-07-11

## 1. Проблема

Базы знаний сегодня — это коллекции документов. Статья про RTX 5070, статья про выбор видеокарты, статья про архитектуру Blackwell. Каждый документ самодостаточен, содержит свою копию фактов и аналитики. При обновлении одного факта (например, TDP видеокарты) нужно править десятки документов. Одна и та же инженерная модель дублируется в обзорах, сравнениях, гайдах и обучающих материалах.

Это проблема композиции, а не хранения. Факты и модели уже есть. Они просто не переиспользуются.

## 2. Видение

**Knowledge Services** — композиционный движок знаний, в котором:

- Знания хранятся один раз на своём уровне абстракции
- Статьи, обзоры, сравнения и гайды — это композиции существующих знаний, а не самостоятельные документы
- Одно и то же знание (инженерная модель, факт, метрика) используется в десятках представлений без дублирования

База знаний перестаёт быть набором документов и становится графом композиций, где верхние уровни собираются из нижних.

## 3. Ключевая идея

Atomic Design, адаптированный для знаний:

| Классический Atomic Design | Knowledge Base | Суть уровня |
|---|---|---|
| Atoms | **Primitives** | Неделимые единицы знания |
| Molecules | **Components** | Устойчивые композиции знаний |
| Organisms | **Modules** | Законченные инженерные модели |
| Templates | **Views** | Аналитические схемы/представления |
| Pages | **Artifacts** | Статьи, обзоры, гайды — конечный продукт |

**Фундаментальное правило:** нижние уровни не знают о верхних. Primitive не знает, в какой Artifact попадёт. Module не знает, в скольких Views будет использован. Только верхние уровни определяют композицию.

Это превращает базу знаний в композиционный движок. При обновлении Module (например, микроархитектуры GB205) все Artifact'ы, использующие этот Module, получают обновление автоматически.

## 4. Две ортогональные оси

Knowledge Services опирается на разделение двух осей:

| Ось | Методология | Вопрос |
|---|---|---|
| Онтология | **DDD** | Что существует? Какие сущности, агрегаты, bounded contexts? |
| Композиция | **Atomic Design** | Как представления собираются из сущностей? |

DDD определяет границы моделей и их отношения. Atomic Design определяет иерархию композиции представлений. Это не альтернативы — это ортогональные измерения. Atomic Design не заменяет DDD, а становится архитектурой представлений *над* DDD-моделью.

## 5. Уровни композиции

### 5.1 Primitives — неделимые знания

Атомы знаний, которые нельзя логически разложить дальше. Словарь предметной области. Типы примитивов:

- **Concept** — понятие (GPU, VRAM, PCIe Lane)
- **Metric** — измеримая величина (TDP 250W, Boost Clock 2.5 GHz)
- **Observation** — зафиксированный факт из тестирования (FPS в игре)
- **Specification** — заявленная производителем характеристика (16 GB GDDR7)
- **Law** — физический/инженерный закон (пропускная способность = частота × ширина шины / 8)
- **Relation** — связь между сущностями (RTX 5070 использует GB205)

Никакой аналитики. Только факты.

### 5.2 Components — устойчивые композиции

Связанные примитивы, образующие осмысленную единицу. Появляется семантика:

- Memory Subsystem = VRAM + Bus Width + Bandwidth + Compression
- Rendering Pipeline = Raster + RT + Tensor
- Power Delivery = TDP + Transient Spike + Connector + PSU Requirement

### 5.3 Modules — законченные инженерные модели

Полные описания подсистем или продуктов:

- GPU Architecture (GB205)
- Compute Pipeline
- Memory Architecture
- Power Architecture
- Display Engine

Module может быть как спецификацией продукта (GB205), так и инженерной моделью (Memory Architecture).

### 5.4 Views — аналитические схемы

Шаблоны, определяющие структуру анализа. Не содержат контента — только схему:

- GPU Analysis: Architecture → Memory → Power → Performance → Tradeoffs → Envelope → Recommendations
- CPU Review: Architecture → Cache → Memory Controller → Platform → Benchmarks → Positioning
- Comparison: Context → Dimensions → Side-by-side → Verdict

### 5.5 Artifacts — конечные продукты

Конкретные страницы: обзоры, сравнения, гайды, статьи. Собираются композицией View + конкретных Modules/Components/Primitives:

- RTX 5070 Review = GPU Analysis View + GB205 Module + 16GB GDDR7 Component + Benchmarks + Price
- RTX 5070 vs RX 9070 XT = Comparison View + два GPU Module + Memory Components

Artifact почти ничего своего не содержит. Он — композиция.

## 6. Требования

### 6.1 Функциональные

- **FR-1:** Примитивы, компоненты и модули создаются один раз и переиспользуются в неограниченном числе артефактов
- **FR-2:** Обновление модуля автоматически отражается во всех артефактах, которые его используют
- **FR-3:** Система поддерживает multiple views над одной онтологией: один и тот же Module может быть представлен в обзоре, сравнении, гайде и обучающем материале
- **FR-4:** Навигация по уровням: от Artifact вниз к составляющим его Primitives
- **FR-5:** Query layer: найти все артефакты, использующие конкретный Module или Primitive

### 6.2 Нефункциональные

- **NFR-1:** Хранение в git-репозитории — markdown + YAML frontmatter
- **NFR-2:** LLM-friendly: структура должна быть нативной для языковых моделей, без промежуточных трансформаций
- **NFR-3:** Никаких баз данных — файловая система как граф композиций

## 7. Границы (out of scope)

- **Не** CMS и не headless CMS — это не система управления контентом
- **Не** SSG (Static Site Generator) — генерация HTML/MDX — отдельная ответственность
- **Не** замена DDD — онтология моделируется в DDD, композиция — в Atomic Design
- **Не** визуальный билдер — композиция описывается декларативно, не drag-and-drop
