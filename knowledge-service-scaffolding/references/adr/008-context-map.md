# ADR-008: Намерение использовать Context Map для интеграции bounded contexts

## Контекст

ADR-001 установил DDD как онтологическую ось. ADR-007 определил workspace как набор изолированных контекстов (директорий) и зарезервировал `context-map.md` как служебный файл для связей между ними.

Изолированные контексты не существуют в вакууме. Знания из одного контекста нужны в другом. `equipment/` описывает помпу с давлением 9 bar, `coffee/` использует эту характеристику в модели экстракции. Без явного описания этих связей workspace либо распадётся на несвязанные острова, либо контексты начнут неявно ссылаться друг на друга, разрушая изоляцию.

Нужно зафиксировать намерение: каким понятийным аппаратом мы описываем связи между контекстами. Реализация — позже.

## Решение

**Мы намерены применять карту контекстов (Context Map) из DDD** как понятийный аппарат для описания отношений между изолированными контекстами.

Context Map — это не формат файла, не синтаксис, не реализация. Это vocabulary: набор типов отношений, которыми мы описываем, как один контекст зависит от другого и как они взаимодействуют.

### Типы отношений между контекстами

| Паттерн | Суть |
|---|---|
| **Партнёрство (Partnership)** | Команды двух контекстов кооперируются, согласовывают изменения и могут влиять на модели друг друга. Контракт подвижен |
| **Общее ядро (Shared Kernel)** | Контексты разделяют небольшую общую часть модели (например, базовые типы). Требует высокой синхронизации. Рекомендуется минимизировать |
| **Поставщик–Потребитель (Customer–Supplier)** | Поставщик (upstream) предоставляет данные, потребитель (downstream) зависит от них. Поставщик учитывает нужды потребителя, но доминирует |
| **Конформист (Conformist)** | Потребитель безоговорочно следует модели поставщика, не имея права влиять на контракт. Типично при интеграции с внешними источниками |
| **Слой антикоррупции (Anticorruption Layer, ACL)** | Потребитель строит изолирующий слой-переводчик, защищая свою модель от чужой. Модель поставщика не просачивается внутрь |
| **Открытая хост-служба (Open Host Service, OHS)** | Контекст-поставщик предоставляет единый протокол для всех желающих, часто с отдельной моделью для интеграции |
| **Публикуемый язык (Published Language)** | Формальный общий язык для общения контекстов (схема, спецификация), часто в паре с OHS |
| **Раздельные пути (Separate Ways)** | Контексты не интегрируются вообще. Допустимо дублирование ради изоляции |

### Контекст может выступать в разных ролях

Один и тот же контекст может иметь разные типы отношений с разными соседями:

- Для `coffee/` контекст `equipment/` может быть **Customer–Supplier**: equipment предоставляет характеристики устройств, coffee их потребляет
- Для внешнего источника данных (datasheet'ы производителей) контекст `equipment/` может использовать **Conformist** + **ACL**: модель поставщика не должна просачиваться внутрь equipment
- Два контекста `coffee/` и `tea/` могут быть в **Partnership**: команды согласовывают общую модель заваривания

Выбор паттерна зависит от организационных отношений, способности влиять на контракт и требуемой степени изоляции модели.

## Что мы НЕ фиксируем сейчас

- Формат `context-map.md` (YAML, markdown, граф, отдельные файлы)
- Механизм enforcement паттернов (как ACL реализован в файловой KB)
- Инструментарий валидации кросс-контекстных ссылок
- Синтаксис описания отношений

Всё это — предмет будущих ADR. Сейчас фиксируется только vocabulary: какими понятиями мы описываем отношения.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему нет |
|---|---|---|---|
| Без карты контекстов — ссылки напрямую | Простота | Разрушает изоляцию. Изменение `equipment/` неожиданно ломает `coffee/` | Противоречит ADR-001 и ADR-007 |
| Только один тип связи («зависит от») | Предельная простота | Не различает Partnership и Conformist. Теряется информация о природе отношений | Бедный vocabulary порождает неявные соглашения |
| Полносвязный граф (каждый с каждым) | Максимальная гибкость | N² связей при N контекстов. Невозможно рассуждать о системе | Context Map — intentional design, не автоматическая индексация |
| Свой формат, не DDD Context Map | Независимость от DDD-терминологии | Изобретаем велосипед. DDD Context Map — проверенный vocabulary | Нет причин не использовать готовый |

## Последствия

**Что становится проще:**
- Проектирование интеграций: выбор из известных паттернов, а не изобретение каждый раз
- Коммуникация: «между coffee и equipment — Customer–Supplier» понятно всем, кто знает DDD
- Аудит: видно, где ACL защищает модель, а где Conformist пропускает чужое без фильтрации

**Что усложняется:**
- Требует знания DDD Context Map от всех участников
- Паттерн нужно выбрать consciously — нельзя просто «связать» контексты

**Что требует внимания:**
- Не использовать все паттерны сразу. На старте достаточно Partnership, Customer–Supplier, Conformist и Separate Ways
- Shared Kernel — опасный паттерн, требует постоянной синхронизации. Использовать только когда два контекста действительно делят модель
- Big Ball of Mud не включён в vocabulary намеренно — это не паттерн для применения, а антипаттерн для исправления
