# ADR-007: Структура workspace — файловая проекция bounded contexts

## Контекст

ADR-001 установил две ортогональные оси: DDD (онтология) и Atomic Design (композиция). ADR-002 определил пять уровней композиции: Primitives → Components → Modules → Views → Artifacts. ADR-006 зафиксировал, что всё это — просто файлы.

Но остаётся неопределённым: как эти оси проецируются на файловую систему? Где проходит граница между bounded context'ами? Как выглядит workspace — корень конкретной knowledge base?

Решение должно быть нативным для файловой системы: структура директорий должна быть самодокументированной. Агент, зайдя в workspace, должен понять его устройство без чтения внешней документации.

## Решение

### Workspace — корень knowledge base

Workspace — это директория, содержащая изолированные контексты. Сам workspace не содержит знаний — только контексты и служебные файлы.

```
my-knowledge-base/                  # workspace
├── index.md                        # карта workspace: какие контексты есть
├── context-map.md                  # связи между контекстами (служебный)
├── coffee/                         # изолированный контекст
│   ├── index.md                    # описание контекста
│   ├── primitives/
│   ├── components/
│   ├── modules/
│   ├── views/
│   └── artifacts/
├── equipment/                      # изолированный контекст
│   ├── index.md
│   ├── primitives/
│   ├── components/
│   ├── modules/
│   ├── views/
│   └── artifacts/
└── chemistry/                      # изолированный контекст
    ├── index.md
    ├── primitives/
    └── ...
```

### Изолированный контекст — директория с семантическим именем

Каждый bounded context — это директория с именем, отражающим его семантику: `coffee/`, `equipment/`, `chemistry/`. Имя — это и есть идентификатор контекста.

Внутри контекста — пять стандартных директорий, по одной на каждый уровень композиции (ADR-002):

| Директория | Уровень | Назначение |
|---|---|---|
| `primitives/` | Primitives | Неделимые знания — Concepts, Metrics, Observations, Specifications, Laws, Relations |
| `components/` | Components | Устойчивые композиции Primitives |
| `modules/` | Modules | Законченные модели |
| `views/` | Views | Аналитические схемы |
| `artifacts/` | Artifacts | Конечные продукты — статьи, обзоры, гайды |

Директории создаются пустыми при инициализации контекста. Они существуют как structural scaffolding — агент сразу видит, куда класть знания каждого уровня.

### index.md контекста — самодокументирование

Каждый контекст содержит `index.md`, который описывает:
- Что это за контекст (назначение, границы)
- Какие сущности в него входят
- Какие правила действуют внутри контекста

`index.md` **не описывает связи с другими контекстами**. Он документирует контекст изнутри, не его внешние отношения. Это preserving изоляции: контекст должен быть понятен без чтения других контекстов.

### context-map.md — связи между контекстами

Связи между контекстами вынесены в отдельный служебный файл на уровне workspace: `context-map.md`.

**Формат:** уточняется. На данном этапе фиксируется только существование файла и его назначение. Возможные форматы: DDD Context Map ( partnership, shared kernel, customer-supplier, conformist, anticorruption layer, open host service), граф зависимостей, directed links.

**Правило:** ни один файл внутри контекста не ссылается на другой контекст напрямую. Если `coffee/components/brewing-parameters.md` использует `equipment/primitives/pump-pressure.md`, эта связь описывается в `context-map.md`, не внутри компонента. Это сохраняет изоляцию контекстов и предотвращает неявные зависимости.

### index.md workspace — карта knowledge base

Корневой `index.md` содержит:
- Список всех контекстов с краткими описаниями
- Ссылку на `context-map.md`
- Метаданные workspace (владелец, домен, версия схемы)

Агент, зайдя в workspace, читает корневой `index.md` → понимает, какие контексты есть → заходит в нужный контекст → читает его `index.md` → работает с файлами внутри.

## Обоснование

1. **Нативность для файловой системы.** Структура не требует парсинга или индексации. `ls` — это уже навигация по контекстам и уровням.

2. **Изоляция контекстов.** Контексты не знают друг о друге. Изменение `equipment/` не затрагивает `coffee/`, если связь не описана в `context-map.md`.

3. **Самодокументирование.** Каждый уровень структуры содержит `index.md`. Агент ориентируется в workspace через progressive disclosure: workspace index → context index → файлы знаний.

4. **Предсказуемость.** Пять стандартных директорий внутри любого контекста. Агент всегда знает, где искать Primitives контекста `X`: `X/primitives/`.

5. **Scaffolding.** Пустые директории — это invitation: «здесь будут знания этого уровня». Агент видит структуру до того, как она заполнена.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему нет |
|---|---|---|---|
| Плоская структура (все файлы в одной директории) | Предельная простота | Нет изоляции контекстов. Нет progressive disclosure. При 100+ файлах — свалка | Нарушает DDD-ось (ADR-001) |
| Один файл = один уровень (primitives.md, components.md) | Меньше файлов | Файлы становятся гигантскими. Нельзя править один Primitive изолированно. Git diff по файлу из 5000 строк бесполезен | Противоречит Premise 3 (ADR-006) |
| Контексты как git submodules | Максимальная изоляция, независимые истории | Overhead управления submodules. Невозможно атомарное изменение, затрагивающее два контекста | Избыточно для KB, где контексты связаны |
| Автогенерация структуры по конфигу | Гибкость | Агент не видит структуру до парсинга конфига. Нарушает «KB — это просто файлы» | Противоречит ADR-006 |

## Последствия

**Что становится проще:**
- Инициализация workspace: создать директории — workspace готов
- Навигация: структура директорий = карта knowledge base
- Изоляция: работа в `coffee/` не ломает `equipment/`
- Миграция: перенести контекст = скопировать директорию

**Что усложняется:**
- Кросс-контекстные запросы: «найти все Primitives, используемые и в coffee, и в equipment» требует чтения `context-map.md` и навигации по двум директориям
- Дублирование Primitives на границе контекстов: Pump Pressure нужен и в `equipment/`, и в `coffee/`. В каком контексте он живёт? Решается `context-map.md` (один контекст — владелец, остальные ссылаются)

**Что требует внимания:**
- Формат `context-map.md` должен быть определён до первого кросс-контекстного знания
- Не создавать контексты про запас. Контекст появляется, когда появляется bounded context в DDD-модели
- Не допускать «общего» контекста (`shared/`, `common/`). Если знание используется в нескольких контекстах — оно принадлежит одному из них, остальные ссылаются через context-map
