# ADR-003: Downward-visibility rule — нижние уровни не знают о верхних

## Контекст

В классическом Atomic Design действует правило однонаправленной зависимости: Button не знает, что окажется в Checkout Page. Molecules знают только о своих Atoms. Нижние уровни ничего не знают о верхних.

При переносе на Knowledge Base это правило критически важно, но неочевидно. Типичная база знаний работает наоборот: документ содержит всё знание внутри себя. Статья про эспрессо включает и спецификации оборудования, и параметры заваривания, и анализ вкуса. Знание не переиспользуется — оно продублировано в каждом документе.

Без этого правила Knowledge Services вырождается обратно в коллекцию самодостаточных документов.

## Решение

**Правило:** уровень N не имеет ссылок, импортов или зависимостей от уровней N+1 и выше.

| Уровень | Знает о | Не знает о |
|---|---|---|
| Primitive | Ничего (или другие Primitives на том же уровне) | Components, Modules, Views, Artifacts |
| Component | Primitives | Modules, Views, Artifacts |
| Module | Components, Primitives | Views, Artifacts |
| View | Modules, Components, Primitives | Artifacts (View определяет схему, но не знает конкретных Artifacts) |
| Artifact | Все нижние уровни | Другие Artifacts (композиция, не ссылка) |

**Пример нарушения:** Module Espresso Extraction Model содержит «Этот модуль используется в Espresso Brewing Guide». Это недопустимо. Module не знает, где он используется.

**Пример соблюдения:** Artifact «Espresso Brewing Guide» объявляет: я собираюсь из View Process Guide + Module Espresso Extraction Model + Component Brewing Parameters. Только Artifact знает о композиции. Module Espresso Extraction Model ничего не знает об этом Artifact.

## Обоснование

1. **Переиспользование.** Если Module знает, где используется, он привязан к контексту. Если не знает — он может быть использован в обзоре, сравнении, гайде и обучающем материале без изменений.

2. **Обновления.** При изменении Module (например, уточнение модели экстракции) все Artifacts получают обновление автоматически — не нужно править каждый документ.

3. **Разделение ответственности.** Автор Module думает только о корректности инженерной модели. Автор Artifact думает только о композиции и нарративе. Они не блокируют друг друга.

4. **Граф композиции.** При соблюдении правила граф зависимостей становится направленным ациклическим графом (DAG) от Artifacts вниз. Это позволяет автоматически отвечать на вопросы: «В каких Artifacts используется Module X?», «Какие Primitives нужно обновить при изменении характеристики Y?»

## Альтернативы

| Вариант | Плюсы | Минусы | Почему нет |
|---------|-------|--------|------------|
| Двунаправленные ссылки (Module знает о своих Artifacts) | Удобная навигация в обе стороны | Module теряет независимость; изменение контекста использования ломает Module | Нарушает переиспользование |
| Плоская структура (все ссылаются на всех) | Максимальная гибкость | Хаос; граф зависимостей становится циклическим | Невозможно автоматизировать обновления |
| Только один уровень (всё — Artifacts) | Простота | Возврат к статус-кво: документы дублируют знания | Противоречит самой идее Knowledge Services |

## Последствия

**Что становится проще:**
- Аудит: всегда известно, что затронет изменение Module (все Artifacts, которые его используют)
- Кеширование/сборка: Artifact можно пересобрать, зная только его декларацию композиции
- Независимая работа: автор Module и автор Artifact не конфликтуют

**Что усложняется:**
- Навигация «снизу вверх» требует query layer: чтобы узнать, где используется Module, нужен индекс
- Автор Module не видит контекста использования — может создать модель, которая плохо ложится в типовые Views. Требуется coordination через View design
- При удалении Module нужно найти и обработать все Artifacts, которые на него ссылаются

**Что требует внимания:**
- Механизм обнаружения использования: нужен индекс «Module → Artifacts», обновляемый при каждом изменении композиции
- Не допускать «soft references» в prose: если в тексте Module написано «как мы увидим в обзоре...», это нарушение правила
