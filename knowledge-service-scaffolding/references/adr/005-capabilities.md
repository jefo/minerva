# ADR-005: Capabilities как composable-единицы minerva skill

## Контекст

minerva — имплементация Knowledge Services. Это Hermes-скилл, который должен предоставлять функциональность для работы с композиционным движком знаний: создание Primitives, сборка Components и Modules, формирование Views, компиляция Artifacts.

Но сам скилл — не монолит. Его функциональность будет расти: сначала query layer, потом валидация, потом компиляция Artifacts, потом интеграции. Нужен способ наращивать скилл без переписывания и без превращения SKILL.md в простыню на 5000 строк.

Возникает вопрос: из чего состоит minerva skill и как он растёт?

## Решение

**Capability** — атомарная единица функциональности minerva skill. Capability покрывает одну операцию или один bounded context внутри Knowledge Services. Сам скилл — композиция capabilities.

### Свойства capability

| Свойство | Описание |
|---|---|
| **Ограниченная ответственность** | Одна capability = одна операция или один bounded context. Не «работа с примитивами», а «создание и валидация Primitives» |
| **Самодостаточность** | Capability содержит всё необходимое для своей операции: правила, шаблоны, валидацию. Не требует чтения других capabilities для работы |
| **Контракт** | У каждой capability явный вход (что принимает) и выход (что производит). Другие capabilities и оркестратор полагаются на контракт, не на внутренности |
| **Композируемость** | Capabilities компонуются в workflows: «создать Primitive → валидировать → сохранить». Одна capability может вызывать другую через контракт |
| **Независимое развитие** | Capability можно добавить, изменить или заменить, не трогая остальные. Новая capability «валидация Laws» не ломает «создание Metrics» |

### Структура capability

Каждая capability — это поддиректория внутри `minerva/`:

```
minerva/
├── SKILL.md                        # Точка входа — оркестратор
├── capabilities/
│   ├── primitive-create/           # Создание Primitives
│   │   ├── SKILL.md                # Локальный скилл: правила, шаблоны
│   │   └── references/             # Схемы, валидаторы
│   ├── primitive-validate/         # Валидация Primitives
│   │   └── SKILL.md
│   ├── component-compose/          # Сборка Components из Primitives
│   │   └── SKILL.md
│   ├── query-layer/                # Поиск по уровням композиции
│   │   └── SKILL.md
│   └── artifact-compile/           # Компиляция Artifact из View + Modules
│       └── SKILL.md
└── src/                            # Код (если нужен)
```

**Правило:** capability — это всегда директория с `SKILL.md`. Это позволяет capability самой быть мини-скиллом со своими правилами, шаблонами и references.

### Оркестратор

`minerva/SKILL.md` — оркестратор. Он не содержит реализации операций. Он:

1. Знает список всех capabilities и их контракты
2. Маршрутизирует запросы пользователя к нужной capability
3. Компонует capabilities в workflows («создай Primitive и сразу провалидируй»)

Оркестратор — это **composition root** minerva skill. Capabilities — **leaves**.

### Связь с архитектурой уровней (ADR-002)

Capabilities НЕ являются уровнями композиции знаний. Это другая ось:

| Ось | Что определяет | Метод |
|---|---|---|
| Уровни знаний (ADR-002) | Структура самой Knowledge Base | Primitives → Components → Modules → Views → Artifacts |
| Capabilities (ADR-005) | Функциональность скилла, работающего с KB | primitive-create, query-layer, artifact-compile |

Одна capability может работать с несколькими уровнями. Например, `query-layer` ищет по всем уровням. `artifact-compile` работает c View и Module.

Но **каждая capability знает, с какими уровнями она работает**, и это часть её контракта.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему нет |
|---------|-------|--------|------------|
| Монолитный SKILL.md | Простота | Немасштабируемо: при 5+ операциях файл становится нечитаемым. Нельзя разрабатывать параллельно | Расти будет быстро |
| Один файл на операцию (без директорий) | Плоско, легко найти | Нет места под references/ и шаблоны для каждой операции. Валидация Primitives требует своих схем — где их хранить? | Capability часто требует своих артефактов |
| Микросервисы (отдельные скиллы Hermes) | Максимальная изоляция | Фрагментация: пользователю нужно знать 10 имён скиллов вместо одного `minerva`. Оркестрация между скиллами — overhead | minerva — один продукт, должен быть одной точкой входа |
| Плагины (как в Hermes tools) | Динамическая загрузка | Избыточно для 5-10 capabilities. Усложняет разработку без выигрыша на старте | Преждевременная сложность |

## Последствия

**Что становится проще:**
- Наращивание: новая capability = новая директория, оркестратор узнаёт о ней. Ничего не ломается
- Параллельная разработка: два разработчика могут делать `primitive-validate` и `query-layer` независимо
- Тестирование: capability тестируется изолированно — дали вход, проверили выход
- Замена: capability с багом можно заменить, не трогая остальные

**Что усложняется:**
- Оркестратор должен знать контракты всех capabilities — это точка coupling
- При изменении контракта capability нужно обновить оркестратор и все dependent capabilities
- Отладка workflow из 3+ capabilities сложнее, чем отладка монолита

**Что требует внимания:**
- Не создавать capabilities про запас. Capability появляется, когда есть реальная операция. «А вдруг понадобится» — не причина
- Минимальный контракт: capability должна требовать минимум входных данных и возвращать минимум. Не «весь Primitive», а «id + type + payload»
- Оркестратор не должен дублировать логику capabilities. Если оркестратор начинает валидировать Primitives — валидация выносится в capability
