# ADR-006: Knowledge Base as filesystem — фундаментальные premises проекта

## Контекст

Knowledge Services начался не с технологического выбора, а с observation о том, как агенты (Claude Code, Codex, coding agents) уже работают с кодом: они читают файлы, понимают структуру, предлагают изменения, открывают PR. Код живёт в git, проходит review, тестируется до merge.

Почему знания не могут жить так же?

Традиционные базы знаний — это CMS, вики-движки, базы данных. Агент не может «прочитать вики» — ему нужен API. API нужно проектировать, документировать, поддерживать. Каждый новый вид запроса требует нового endpoint. Агент отделён от знаний слоем посредника.

Если знания — это просто файлы, агент работает с ними так же, как с кодом. Без посредников. Без API. Без отличий между «работой с knowledge base» и «работой с репозиторием».

## Решение

### Premise 1: Knowledge Base — это просто файлы

Каждый Primitive, Component, Module, View и Artifact — это `.md` файл с YAML frontmatter в git-репозитории. Никаких баз данных. Никаких CMS. Никаких API между агентом и знанием.

Структура директорий — это и есть структура knowledge base. Имена файлов — это и есть идентификаторы. YAML frontmatter — это и есть метаданные. Markdown — это и есть контент.

**Следствие:** любой инструмент, который умеет читать файлы, уже умеет работать с Knowledge Base. Не нужно писать коннекторы, SDK или API-клиенты.

### Premise 2: Агенты работают с KB без посредников

Claude Code читает knowledge base так же, как читает исходный код проекта. Codex открывает PR с новым Module так же, как с новым компонентом. Агент не различает «я работаю с кодом» и «я работаю со знаниями» — для него это одна и та же операция: прочитать файл, понять контекст, предложить изменение.

**Следствие:** Knowledge Services не нужен собственный агентский фреймворк. Он использует существующие coding agents как есть. Capabilities minerva skill — это всего лишь structured prompts и validation rules, которые направляют агента, но не встают между ним и файлами.

### Premise 3: Git workflow делает рост KB контролируемым

Знания меняются. Новые факты появляются, старые устаревают, модели уточняются. В традиционной KB эти изменения происходят in-place и необратимы. История правок — это лог, не инструмент.

В файловой KB изменения происходят через git:
- **Ветка** = рабочая версия KB, в которой можно экспериментировать с новой моделью
- **Pull Request** = предложение изменить знание, которое проходит review
- **Merge** = знание принято и стало частью основной KB
- **Revert** = знание оказалось ошибочным и откатывается одной командой

**Следствие:** рост KB перестаёт быть хаотичным. Каждое изменение атомарно, обратимо и имеет автора. KB не «разрастается» — она развивается под контролем.

### Premise 4: Агенты могут делать QA над собственной KB

Если KB — это файлы в git, то агент может:
- Валидировать PR перед merge: «не нарушает ли новый Primitive правила композиции?»
- Запускать проверки целостности: «все ли Relation ссылаются на существующие Concepts?»
- Находить проблемы: «какие Artifacts используют Module, который был изменён в этом PR?»
- Блокировать merge при нарушении правил: «этот Component ссылается на несуществующий Primitive»

**Следствие:** качество KB поддерживается не дисциплиной авторов, а автоматическими gate-проверками. Агент-ревьюер следит за правилами композиции так же, как линтер следит за стилем кода.

## Почему это важно: research-driven content pipelines

Перечисленные premises — не самоцель. Они включают конкретный класс workflow, который невозможен в традиционных KB.

**Research-driven content pipeline** — это процесс, в котором:
1. Агент-исследователь собирает сырые данные (Observations, Specifications) в ветку `research/topic`
2. Агент-аналитик собирает из них Components и Modules
3. Агент-редактор компонует Artifact по заданному View
4. Агент-ревьюер проверяет результат на целостность, непротиворечивость и соответствие правилам композиции
5. Человек принимает PR — или отправляет на доработку

В традиционной KB этот процесс невозможен: агентам нужен API, изменения неверсионируемы, нет механизма review. В файловой KB этот процесс — обычный git workflow, просто над markdown-файлами вместо кода.

## Связь с capabilities

Эти premises раскладываются на capabilities minerva skill — выраженные на языке бизнес-операций, не реализации:

| Premise | Выраженная как capability |
|---|---|
| KB — это файлы | **Primitive Creation** — создать новый `.md` файл с frontmatter. **Query Layer** — найти существующий Primitive по пути или метаданным |
| Агенты без посредников | **Knowledge Navigation** — агент читает структуру директорий и понимает, где находится нужный уровень композиции |
| Git workflow | **Change Proposal** — создать ветку, внести изменения, открыть PR. **Knowledge Review** — проверить PR на соответствие правилам композиции |
| Агентское QA | **Integrity Gate** — перед merge проверить, что изменения не ломают ссылки, не дублируют существующие знания, не нарушают downward visibility |

## Альтернативы

| Вариант | Плюсы | Минусы | Почему нет |
|---|---|---|---|
| База данных (SQL, графовая) | Мощные запросы, индексы | Агент не может работать напрямую — нужен API. Изменения неверсионируемы в git. PR невозможен | Противоречит Premise 1 и 2 |
| CMS / Headless CMS | Привычный интерфейс для людей | Агентам нужен API. Структура знаний подчинена структуре контента, а не композиции | Content model ≠ knowledge model |
| Obsidian Vault без git | Простота, [[wikilinks]] | Нет версионирования. Изменения необратимы. Нет PR и review | Противоречит Premise 3 и 4 |
| Специализированный агентский фреймворк | Заточен под KB-операции | Замыкает экосистему: только наши агенты, только наши инструменты. Не использует существующие coding agents | Нарушает Premise 2 |

## Последствия

**Что становится проще:**
- Onboarding агента: `git clone` — и агент уже в контексте всей KB
- Миграция: KB можно перенести на другой хостинг, другого агента, другой процесс — это просто файлы
- Отладка: `git log -- knowledge-base/primitives/espresso.md` показывает всю историю изменений знания
- Коллаборация: человек и агент работают в одном репо, через одни и те же PR

**Что усложняется:**
- Производительность на больших объёмах: grep по 10 000 файлов медленнее, чем SQL-запрос. Решается структурой директорий и индексными файлами
- Конкурентные изменения: два агента не могут одновременно править один файл. Решается git-ветками
- Нет транзакций: изменение, затрагивающее 50 файлов — это 50 отдельных коммитов или один большой. Решается дисциплиной PR: одно изменение = один PR

**Что требует внимания:**
- Файловая KB не должна превратиться в «свалку .md файлов». Структура директорий — это часть онтологии, не просто организация
- Git не решает конфликты знаний. Если два агента предлагают противоречащие факты — git разрешит merge conflict в тексте, но не разрешит conflict в знании. Нужен семантический diff
- Не заводить базу данных «потом». Premise 1 — это осознанный архитектурный выбор, не временное решение
